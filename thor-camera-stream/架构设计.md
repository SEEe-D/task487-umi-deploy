# Thor 6路相机低延迟推流工具 — 架构设计

## 1. 系统概述

将Thor上的6路GMSL相机画面，通过直连以太网以UDP RTP方式推送到PC，为模型推理提供实时视频输入。

**核心指标:**
- 传输分辨率: 可配置, 默认480×480 (从1920×1536硬件缩放)
- 帧率: 25fps (GPIO FSIN硬件同步, 与UMI数采一致)
- 端到端延迟: <50ms (网线直连)
- 编码码率: 可配置, 默认4Mbps/路 (高质量)

```
┌─────────────────────────────────────────────┐     ┌──────────────────────────────────────────┐
│           Thor (推流端)                       │     │           PC (接收端)                      │
│                                             │     │                                          │
│  IMX307 ×6                                  │     │                                          │
│  1920×1536 UYVY                             │     │                                          │
│      │                                      │     │                                          │
│      ▼                                      │     │                                          │
│  V4L2 (v4l2src)                             │     │                                          │
│      │                                      │     │                                          │
│      ▼                                      │     │                                          │
│  nvvidconv (硬件缩放+NV12转换)               │     │                                          │
│      │                                      │     │                                          │
│      ▼                                      │     │                                          │
│  nvv4l2h264enc (Tegra硬件H264编码)           │     │  udpsrc (接收UDP RTP包)                    │
│      │  ← 4Mbps CBR, 无B帧, I帧间隔15       │     │      │                                    │
│      ▼                                      │ UDP │      ▼                                    │
│  rtph264pay (RTP打包)  ─────────────────────┼────>│  rtph264depay → h264parse                 │
│                                             │ RTP │      │                                    │
│                                             │     │      ▼                                    │
│  元数据发送 (frame_id + 时间戳)  ────────────┼────>│  nvh264dec (GPU硬解 / avdec_h264软解回退)   │
│                                             │ UDP │      │                                    │
│                                             │     │      ▼                                    │
│  ClockSyncServer (时钟校准)  ◄──────────────┼────>│  videoconvert (NV12→BGR)                  │
│                                             │ UDP │      │                                    │
│  GPIO FSIN 25Hz (6路相机同步触发)            │     │      ▼                                    │
│                                             │     │  cv2.VideoCapture.read() → numpy BGR数组   │
│                                             │     │      │                                    │
│                                             │     │  ┌───▼────────────────────────────────┐   │
│                                             │     │  │ 2×3网格显示 + OSD                  │   │
│                                             │     │  │ 延迟 / FPS / 丢帧统计 / 帧同步     │   │
│                                             │     │  └───────────────────────────────────┘   │
└─────────────────────────────────────────────┘     └──────────────────────────────────────────┘
```

**三条UDP通道 (每路相机独立):**

| 通道 | 端口 | 内容 | 方向 |
|------|------|------|------|
| 视频 | 5000-5005 | RTP H264视频流 | Thor → PC |
| 元数据 | 6000-6005 | 帧ID+时间戳 (24字节/帧) | Thor → PC |
| 时钟校准 | 7777 | NTP-like偏移测量 | PC ↔ Thor |

## 4. 技术选型

### 4.1 核心技术栈

| 层级 | 推流端 (Thor) | 接收端 (PC) |
|------|--------------|-------------|
| 语言 | Python 3 (GStreamer胶水层) | Python 3 |
| 视频框架 | GStreamer 1.24 (Gst.parse_launch) | OpenCV GStreamer后端 (cv2.VideoCapture) |
| 采集 | v4l2src (V4L2内核驱动) | — |
| 缩放 | nvvidconv (Tegra GPU硬件) | — |
| 编码 | nvv4l2h264enc (Tegra硬件H264) | — |
| 解码 | — | nvh264dec (RTX GPU) / avdec_h264 (CPU回退) |
| 传输 | udpsink (RTP over UDP) | udpsrc |
| 帧同步 | GPIO FSIN 25Hz方波 (gpio_trigger.py) | — |
| 显示 | — | cv2.imshow (OpenCV窗口) |
| 时钟同步 | chrony NTP服务端 + ClockSyncServer | chrony NTP客户端 + UDP校准 |
| 配置 | YAML | YAML |

### 4.2 为什么用Python而不是C++？

Python在本项目中只是GStreamer pipeline的"胶水层"，所有性能关键路径都在GStreamer/硬件层执行：
- 视频采集 (V4L2内核驱动)、硬件编码 (nvv4l2h264enc)、网络发送 (udpsink) 全部是C/硬件完成
- Python只负责pipeline初始化和配置，不参与帧级数据处理
- 接收端 `cap.read()` 返回的就是解码后的numpy BGR数组，可以直接送模型推理
- Python部署更简单：无需交叉编译，scp即用

### 4.3 为什么不用ROS2？

本工具作为独立的推流验证工具：
- ROS2增加额外的序列化/反序列化开销
- ROS2 DDS发现机制引入启动延迟
- 纯GStreamer方案更简洁，延迟更低
- 部署更轻量，无需ROS2环境依赖

## 5. 推流端架构 (Thor)

### 5.1 GStreamer Pipeline (每路相机)

```
v4l2src device=/dev/videoX io-mode=2 do-timestamp=true
  → video/x-raw,format=UYVY,width=1920,height=1536,framerate=60/1
  → queue max-size-buffers=1 leaky=downstream   ← 防止背压, 丢弃旧帧
  → nvvidconv                           ← Tegra GPU硬件缩放
  → capsfilter [video/x-raw(memory:NVMM),width=480,height=480,format=NV12]
  → nvv4l2h264enc                       ← Tegra硬件H264编码
      preset-id=1                       ← 最快编码速度
      bitrate=4000000                   ← 4Mbps CBR (480×480高质量)
      iframeinterval=15                 ← 每15帧一个I帧
      num-B-Frames=0                    ← 无B帧 (减少延迟)
      control-rate=1                    ← CBR恒定码率
      insert-sps-pps=true               ← 每帧附带SPS/PPS (接收端随时可加入)
  → h264parse config-interval=1
  → rtph264pay config-interval=1 pt=96 mtu=1400
  → udpsink host=TARGET_IP port=500X sync=false async=false
```

> - capsfilter的NVMM caps通过 `Gst.Caps.from_string()` 程序化设置，因为 `video/x-raw(memory:NVMM)` 的括号语法在 `Gst.parse_launch` 中会报语法错误。
> - 不使用videorate元素: GPIO FSIN 25Hz已控制相机实际采集帧率，pipeline无需做帧率转换，避免videorate缓冲引入额外延迟。

### 5.2 H264编码与压缩质量

| 参数 | 值 | 说明 |
|------|-----|------|
| 原始数据量 | ~138 Mbps | 480×480×3字节×25fps |
| 编码码率 | 4 Mbps | config.yaml `encoding.bitrate` |
| 压缩比 | ~35:1 | 高质量，肉眼几乎无损 |
| 编码格式 | H.264 Baseline | 无B帧，最低延迟 |

> **关于压缩质量**: `bitrate` 越高画质越好。4Mbps对480×480画质充裕。如需更高画质可调到8Mbps，6路总计48Mbps，千兆网仍只用4.8%带宽。分辨率和码率均为可配置项，见 `sender/config.yaml`。

### 5.3 GPIO FSIN帧同步

6路相机通过GPIO 659 (PM.00引脚) 的25Hz方波信号实现硬件级帧同步:
- gpio_trigger.py 产生方波，控制IMX307的FSIN引脚
- 所有相机在同一个上升沿触发采集，保证6路帧时间对齐
- 移植自UMI数采系统的 dual_trigger.c

### 5.4 时间戳元数据通道

每路相机独立的UDP元数据通道，每帧发送一个24字节包:

```c
struct MetaPacket {      // 24字节, 小端序
    uint32 camera_id;    // 相机编号 0-5
    uint32 frame_id;     // 帧序号 (递增, 用于丢帧检测)
    int64  timestamp;    // 采集时间戳 (微秒, epoch)
    uint32 width;        // 帧宽度
    uint32 height;       // 帧高度
};
```

发送时机: GStreamer rtph264pay的src pad probe回调中，每帧编码完成后发送。

## 6. 接收端架构 (PC)

### 6.1 整体结构

```
                    ┌─────────────────┐
                    │  StreamViewer    │  ← 主线程: 2x3网格显示 + OSD
                    │  cv2.imshow()   │
                    └────────┬────────┘
                             │ 读取最新帧 (每33ms)
              ┌──────────────┼──────────────┐
              │              │              │
     ┌────────▼───┐  ┌──────▼─────┐  ┌─────▼──────┐
     │CameraRecv 0│  │CameraRecv 1│  │CameraRecv 5│  ← 6个子线程
     │ cap.read() │  │ cap.read() │  │ cap.read() │     各自独立GStreamer pipeline
     └────────┬───┘  └──────┬─────┘  └─────┬──────┘
              │              │              │
     ┌────────▼───┐  ┌──────▼─────┐  ┌─────▼──────┐
     │MetaRecv  0 │  │MetaRecv  1 │  │MetaRecv  5 │  ← 6个元数据线程
     │ UDP 6000   │  │ UDP 6001   │  │ UDP 6005   │     接收帧ID+时间戳
     └────────────┘  └────────────┘  └────────────┘
```

- 每路相机1个视频接收线程 + 1个元数据接收线程
- 视频线程: `cv2.VideoCapture(gst_pipeline, cv2.CAP_GSTREAMER)` — OpenCV封装的GStreamer pipeline
- 元数据线程: UDP socket接收帧ID和时间戳，用于延迟计算和丢帧检测
- 主线程: 每33ms (~30fps) 轮询6路最新帧，拼2×3网格，叠加OSD，`cv2.imshow` 显示

### 6.2 接收Pipeline (每路相机)

```
udpsrc port=500X buffer-size=2097152          ← 接收UDP RTP包 (2MB缓冲)
  → application/x-rtp,encoding-name=H264,payload=96
  → rtph264depay                              ← RTP解包
  → h264parse
  → nvh264dec (或 avdec_h264)                 ← GPU硬解 (失败自动回退CPU软解)
  → queue max-size-buffers=1 leaky=downstream ← 低延迟: 只保留最新帧
  → videoconvert                              ← NV12→BGR颜色转换
  → video/x-raw,format=BGR
  → appsink sync=false drop=true max-buffers=1  ← 输出BGR帧给Python, 只缓存1帧
```

`cv2.VideoCapture.read()` 从appsink取出解码后的BGR numpy数组，可直接用于:
- OpenCV显示 (`cv2.imshow`)
- 模型推理 (numpy数组 → torch tensor)

### 6.3 OSD显示

每路画面叠加 (cv2.putText + LINE_AA抗锯齿, 字号/行距按 `s = h/480.0` 自适应缩放):
- 第1行: 相机英文标签
- 第2行: 端到端延迟 (绿<50ms, 黄<100ms, 红>100ms)
- 第3行: 接收FPS + 解码器类型
- 第4行: 帧统计 F:接收帧数 D:丢帧数 (丢帧时红色)

底部状态栏:
- Connected: 已连接相机数
- Avg Latency: 平均延迟
- Sync: 6路latency最大差值 (反映显示画面的时间同步程度, 越小越同步)
- Drop: 总丢帧数和丢帧率
- Offset: 时钟偏移

### 6.4 丢帧检测

通过元数据中的 `frame_id` 连续性检测:
- 推流端每帧递增 frame_id (1, 2, 3, ...)
- 接收端检查相邻 frame_id 的间隔
- 间隔 > 1 表示中间有帧丢失
- OSD显示: F:帧数 D:丢帧数 (有丢帧时红色高亮)

### 6.5 延迟与同步计算

```
每路延迟 = T_receive - (T_send - clock_offset)
帧同步   = max(各路延迟) - min(各路延迟)
```

- T_send: 推流端编码完成时的 `time.time()` (rtph264pay pad probe)
- chrony保证两机系统时钟同步 (<0.1ms)
- UDP辅助校准: 启动时测量 + 每30秒自动重新校准
- EMA平滑 (alpha=0.15) 避免数值跳动
- 帧同步 (Sync): 6路latency最大差值, 反映显示画面的时间一致性
- 采集同步由GPIO FSIN硬件保证, Sync衡量的是显示端同步

### 6.6 模型集成说明

算法工程师集成receiver代码时，核心类是 `CameraReceiver`。不需要显示UI时，去掉 `StreamViewer` 和 `cv2.imshow`，只保留 `CameraReceiver` + `MetaReceiver`。

```python

    if len(frames) == 6:
        # cv2.resize(frame, (224, 224)) 缩放到模型输入尺寸
        # torch.from_numpy(frame).permute(2,0,1).float() / 255.0 转tensor
        pass

# 4. 停止
for r in receivers:

```

**关键说明:**
- **frame格式**: `numpy.ndarray`, shape=`(H, W, 3)`, dtype=`uint8`, 颜色空间BGR
- **分辨率**: 与 `sender/config.yaml` 中的 `stream_resolution` 一致 (当前480×480)
- **线程安全**: 取帧时必须用 `with r.lock` 加锁
- **无帧时**: `r.frame` 为 `None`，等推流端数据到达后自动更新

## 7. 时钟同步方案

采用**双层时钟同步架构**:

### 7.1 chrony NTP (主要) — 系统级

PC作为NTP服务器，Thor通过chrony持续同步到PC，精度<0.1ms。

- chrony是Linux标准时钟服务，通过微调时钟频率保持同步，**不影响其他系统功能**
- 配置一次后开机自动生效
- 详细配置见 README.md §2

### 7.2 UDP辅助校准 (兜底) — 应用层

接收端内置UDP NTP-like校准机制，作为chrony的补充:
- 推流端 `ClockSyncServer` 监听UDP 7777
- 接收端启动时15样本探测，按最小RTT取中位数offset
- 每30秒自动重新校准
- 配好chrony后offset通常<1ms

## 8. 带宽估算

| 参数 | 值 |
|------|-----|
| 单路码率 | 4 Mbps |
| 6路总码率 | 24 Mbps |
| 元数据开销 | <0.01 Mbps |
| 千兆以太网带宽 | 1000 Mbps |
| 带宽利用率 | ~2.4% |

带宽极其充裕。即使码率提升到8Mbps/路 (48Mbps总计)，千兆网也仅用4.8%带宽。

## 9. 延迟分析

| 环节 | 预估延迟 |
|------|---------|
| V4L2采集 (1帧@25fps) | ~40ms (帧间隔) |
| 硬件H264编码 (nvv4l2h264enc) | ~5ms |
| 网络传输 (直连以太网UDP) | <1ms |
| RTP解包 + H264解码 (nvh264dec) | ~5ms |
| videoconvert + OpenCV渲染 | <1ms |
| **总计** | **~52ms** |

> 实际延迟主要受帧间隔限制。25fps帧间隔40ms是理论下限。
